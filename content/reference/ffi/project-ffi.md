Project FFI is the build-time path for application-owned C bindings.

It lets one project compile its own C files alongside the kernel without turning those words into board-level API.

## The contract in `froth.toml`

Project FFI is declared under `[ffi]`:

```toml
[ffi]
sources = ["src/ffi/bindings.c"]
includes = ["src/ffi"]
defines = { SENSOR_SCALE = "42" }
```

The fields mean:

- `sources`: project-local `.c` files
- `includes`: include directories passed to the compiler
- `defines`: preprocessor definitions

If `[ffi]` is absent, no project FFI is built.

## The required symbol

Project FFI must export a null-terminated table named:

```c
const froth_ffi_entry_t froth_project_bindings[]
```

That name is fixed because boot code looks for it directly when `FROTH_HAS_PROJECT_FFI` is enabled.

## A complete minimal example

`src/ffi/bindings.c`:

```c
#include "froth_ffi.h"

FROTH_FFI_ARITY(prim_fast_twice, "fast.twice", "( n -- n )", 1, 1,
                "Double a number in C") {
  FROTH_POP(n);
  FROTH_PUSH(n * 2);
  return FROTH_OK;
}

FROTH_BOARD_BEGIN(froth_project_bindings)
  FROTH_BIND(prim_fast_twice),
FROTH_BOARD_END
```

`froth.toml`:

```toml
[ffi]
sources = ["src/ffi/bindings.c"]
includes = ["src/ffi"]
```

After `froth build`, the word is available like any other:

```froth
5 fast.twice .
```

## What the CLI does

The build path lives in `tools/cli/cmd/build.go` and `tools/cli/internal/project/ffi.go`.

When `froth build` runs in a project:

1. the manifest is loaded
2. `[ffi]` is resolved and validated
3. the CLI writes `.froth-build/project_ffi.cmake`
4. CMake is invoked with `-DFROTH_PROJECT_FFI_CONFIG=...`

The config fragment contains three lists:

```cmake
set(FROTH_PROJECT_FFI_SOURCES ...)
set(FROTH_PROJECT_FFI_INCLUDES ...)
set(FROTH_PROJECT_FFI_DEFINES ...)
```

That file is generated by `prepareProjectFFIConfig(...)` in `tools/cli/cmd/build.go`.

## Validation rules

Validation happens in `ResolveFFI(...)` in `tools/cli/internal/project/ffi.go`.

The rules are intentionally strict:

- `[ffi]` cannot declare includes or defines without sources
- every source must exist
- every source must be a `.c` file
- every source must stay under the project root
- every include path must exist
- every include path must be a directory
- every include path must stay under the project root
- define keys must be valid C identifiers
- define values cannot contain newlines, semicolons, or quotes

Those rules keep project manifests from quietly injecting arbitrary build behavior.

## What CMake does

The kernel `CMakeLists.txt` exposes:

```cmake
set(FROTH_PROJECT_FFI_CONFIG "" CACHE FILEPATH "Optional project FFI config fragment")
```

When that variable is set, CMake:

1. includes the generated fragment
2. adds `FROTH_PROJECT_FFI_SOURCES` to the target
3. adds include directories
4. adds compile definitions
5. defines `FROTH_HAS_PROJECT_FFI`

That is the build-time switch that enables the boot path for `froth_project_bindings`.

## What boot does

`src/froth_boot.c` contains:

```c
#ifdef FROTH_HAS_PROJECT_FFI
extern const froth_ffi_entry_t froth_project_bindings[];
#endif
```

and later:

```c
#ifdef FROTH_HAS_PROJECT_FFI
  err = froth_ffi_register(&froth_vm, froth_project_bindings);
#endif
```

That means project bindings are registered:

- after board bindings
- before snapshot restore
- before `autorun`

From the language point of view, the resulting words are just ordinary slots.

## Ownership boundary

Use project FFI for words like:

- protocol codecs
- application-specific DSP or math helpers
- wrappers around one project's SDK dependency
- small primitives that only one firmware owns

Do not put those words in board FFI unless every project for that board should inherit them.

## Development workflow

The workflow is:

1. add or edit the C file
2. update `[ffi]` in `froth.toml` if needed
3. run `froth build`
4. flash or run the built target
5. keep high-level composition in Froth

`froth send` does not rebuild project FFI. It only evaluates Froth source.

## A good project layout

```text
my-project/
  froth.toml
  src/
    main.froth
    ffi/
      bindings.c
      bindings.h
  lib/
    filters.froth
```

This keeps the ownership line clear:

- `src/ffi/` for the narrow binary edge
- `src/main.froth` and `lib/` for the code you continue reshaping live

## Relation to board libraries

Project FFI does not replace board libraries.

The layering should usually look like this:

- board FFI for target-owned hardware words
- board lib for target-owned Froth wrappers
- project FFI for app-owned C
- project Froth for the actual program

That keeps reusable surfaces reusable and project code local to the project.
